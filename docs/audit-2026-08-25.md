## 1. 重大バグ

### critical

#### B1. レース状態遷移にFINALIZEDガードがなく二重払戻が可能

- 場所: `src/features/admin/manage-races/actions/update.ts` の closeRace / reopenRace / setClosingTime、`src/features/admin/manage-races/actions/payout.ts`
- 内容: closeRace は現在ステータスを確認せず無条件で CLOSED に更新します。FINALIZED のレースに closeRace → finalizePayout を実行すると、finalizePayout のロック後再チェックは status === 'CLOSED' を満たし、全ベットが再処理されます。finalizePayout はベットを status で絞らず全件取得するため、払戻済みの HIT ベットにも再度ウォレット加算とトランザクション挿入が走ります。reopenRace / setClosingTime も FINALIZED から SCHEDULED に戻せるため、確定後のレースにベット追加も可能です。管理者の誤操作1回で全ウォレットの整合性が壊れます。
- 対応: 状態遷移に前提ステータスのガードを追加。finalizePayout は PENDING のベットのみ処理対象にする。

### high

#### B2. 無認可のserver actionで他人の残高・取引履歴・ベットを読める

- 場所: `src/features/economy/wallet/queries.ts` の getWalletTransactions / getEventWallets、`src/features/admin/manage-bets/actions/read.ts` の getBetsByRace
- 内容: いずれも 'use server' 直下で auth 確認がありません。getWalletTransactions はクライアントコンポーネントから import されておりアクションIDがバンドルに露出しているため、walletId を差し替えるだけで他人の全取引履歴を取得できます。getBetsByRace は全ユーザーのベットを walletId・user リレーション付きで返し、IDの入手経路にもなります。
- 対応: 自分のウォレットかを検証、管理系は requireAdmin を必須化。

#### B3. getUsersがパスワードハッシュとDiscordトークンを返す

- 場所: `src/features/admin/manage-users/queries.ts`
- 内容: requireAdmin がなく、users 全カラムと accounts リレーションを返します。password カラム、email、Discord の access_token / refresh_token が含まれます。
- 対応: requireAdmin 追加と、必要カラムのみの select に変更。

#### B4. BET5の後出し購入が可能

- 場所: `src/features/betting/logic/bet5.ts` の placeBet5Bet
- 内容: bet5Event.status が SCHEDULED であることしか確認せず、対象5レースの状態を見ません。管理者が締切を忘れたまま1レース目を確定させると、結果を見てから的中確定枠を含む購入ができます。
- 対応: 購入時に対象レース全てが SCHEDULED であることを検証。

### medium

#### B5. BET5精算がSCHEDULEDのまま実行でき、精算中の購入代金が消失する

- 場所: `src/features/betting/logic/bet5.ts` の calculateBet5Payout
- 内容: FINALIZED の重複実行だけを拒否し、CLOSED であることを要求しません。精算と購入はロックキーが異なり互いにブロックしないため、精算中に commit された購入は集計にも当選判定にも返金にも含まれません。
- 対応: 精算の前提条件を CLOSED に限定。

#### B6. placeBetsのcombinationsが未検証

- 場所: `src/features/betting/actions.ts`
- 内容: 検証は件数上限と金額の正・100単位のみで、各組み合わせの要素数・整数性・重複・実在馬番との照合がありません。不正なベットが正規データとして払戻集計に混入し得ます。
- 対応: 券種ごとの要素数・整数・馬番範囲・重複を検証。

#### B7. saveEntriesが既存ベットを破壊する

- 場所: `src/features/admin/manage-entries/actions.ts`
- 内容: レース状態やベット有無を確認せず全エントリを削除して馬番を振り直します。ベット受付後に実行すると既存ベットの馬番の意味が変わり、別の馬への投票として精算されます。
- 対応: ベットが存在するレースでは保存を拒否。

#### B8. ランキングのHIDDEN・ANONYMOUSでマスク漏れ

- 場所: `src/features/ranking/actions.ts`
- 内容: HIDDEN でも配列は残高降順のままで実際の順位が漏れます。ANONYMOUS では userId が返却され、他APIと突合すれば匿名化が破れます。
- 対応: マスク時は並び順をシャッフルし userId を返さない。

#### B9. carryoverAmountの競合で増分が消える

- 場所: `src/features/betting/logic/bet5.ts` と `src/features/admin/manage-races/actions/payout.ts`
- 内容: finalizePayout はSQL増分加算、calculateBet5Payout は読み取り値前提の絶対値SETで、並行時に精算側が払戻側の加算を上書きします。
- 対応: 精算側も増減分のSQL演算に変更。

## 2. パフォーマンス

#### P1. use-sseの再接続タイマー未クリアによる接続リーク

- 場所: `src/shared/hooks/use-sse.ts`
- onerror 内の setTimeout(connectSSE, 5000) がクリーンアップで clear されず、アンマウント後に誰も close できない EventSource が生成されます。エラーが続く限り5秒ごとに再接続するゾンビ接続になります。

#### P2. SSEリスナーのenqueueが未ガードで管理アクションを巻き込む

- 場所: `src/app/api/events/race-status/route.ts`
- リスナーは emit 元で同期実行されるため、close 済み controller への enqueue 例外が finalizePayout 等の呼び出し側に伝播し、1クライアントの切断が他ユーザーの操作を失敗させます。あわせて7連コピペハンドラのループ化も行います。

#### P3. getUserBetGroupsForRaceの不要な4階層ネスト取得

- 場所: `src/features/betting/actions.ts`
- 唯一の呼び出し元は bet のフラットな値しか使わず、馬情報は別途取得しています。1000点買いで約18,000個の無駄なネストオブジェクトが生成されます。with を削除します。

#### P4. transactionsの無制限全件取得

- 場所: `src/features/economy/wallet/queries.ts`、`src/features/stats/actions.ts`
- placeBets は1点ごとに transaction を挿入するため、大口ベット数回で数千行になり、履歴ダイアログと統計ページが線形に遅くなります。limit を導入します。

#### P5. 投票ページでSSE接続が1ユーザー2本

- 場所: `src/features/betting/ui/bet-table.tsx`、`src/features/betting/lib/hooks/use-race-odds.ts`
- BetTable が直接 useSSE を呼びつつ useRaceOdds 経由でも接続するため2本張られ、少人数でも MaxListenersExceededWarning が出ます。

#### P6. 管理ページの全イベント×全レース×全出走馬取得

- 場所: `src/features/admin/manage-bets/actions/read.ts`
- クライアントは頭数しか使っていないため、entries の取得を count に置き換えます。

#### P7. getRaceByIdが1リクエストで2回実行

- 場所: `src/app/races/[id]/page.tsx`
- generateMetadata と page 本体が別々に呼ぶため、React の cache() で包みます。

#### P8. odds.tsのsetTimeoutファイア・アンド・フォーゲット

- 単一コンテナ運用では自己回復するため深刻度は低です。サーバーレス移行時にRedisベースへ置き換える構造負債として記録のみ。
