# パフォーマンス特性と検証記録

2026年9月に実施した性能監査の知見をまとめる。
最大30人、低頻度開催という運用想定に足る性能であることを、本番想定の VM 上で確認済みである。
将来、規模の前提が変わったときや応答の劣化を疑ったときに、ここに書いた再現手順で同じ検証を実行できる。

## 結論と全体像

ボトルネックは DB ではなく、Node 単一プロセスによるアプリ層の直列処理である。
30人同時の馬券購入バースト中でも、DB の全クエリ合計は数百ミリ秒に収まる。
開発機で CPU を2コアに制限して比較しても結果はほぼ変わらず、性能を支配するのはシングルコア性能である。
応答時間はコア数やメモリを増やしても改善しない。増強で速くなるのはビルドだけである。

全計測を通して最も遅い操作は馬券購入ではなく、イベント開始時の一斉ログインである。
パスワード照合の bcrypt が CPU を消費するためで、これはユーザー名の存在有無を応答時間から悟らせないための意図的なコストである。
当初の純 JS 実装ではメインスレッドが塞がって照合が直列化し、本番 VM で30人の完了までに約3秒かかっていた。
2026-09-04 に照合をスレッドプールで並列実行する native 実装へ差し替え、開発機の実測で一斉ログインは1.5秒から0.5秒に短縮された。
照合1回の所要時間は差し替え前後でほぼ同じであり、効果は並列化によるものである。

購入の応答時間は、同日にサーバーアクションから revalidatePath を外して半減した。
revalidatePath を呼ぶとアクション応答に対象ページの再レンダリングが同梱され、その描画が購入1件のコストの約半分を占めていた。
対象ページは全て認証付きの動的レンダリングで、購入後は呼び手の router.refresh が取り直し、オッズは SSE が配信するため、外しても表示の鮮度は変わらない。
描画は消えるのではなく refresh 側へ移るため、閲覧の応答時間は不変で、購入の待ち時間だけが短くなる。
開発機の実測で、30人バースト中の購入は中央値464ミリ秒から225ミリ秒、95%点は674ミリ秒から350ミリ秒になった。
E2E で購入後の残高と購入済み一覧の表示更新も検証済みである。

## 計測の再現手順

計測ツールは tools/perf にあり、Taskfile から実行する。

開発環境ではこの順に実行する。

```
task perf:setup            # 30ユーザーと18頭立てレースのフィクスチャを作り直す
task perf:stats:reset      # クエリ統計をリセット
task perf:load -- all      # 8シナリオを一括実行
task db:reconcile          # 負荷後の台帳整合を検証
task perf:clean            # 後片付け
```

本番構成の VM では perf:setup:prod と perf:load:prod を使う。
過去開催の蓄積を再現する場合は `PERF_HISTORY=20 task perf:setup:prod` のように件数を渡す。
クエリ別の実行統計は task perf:stats で見る。
100ミリ秒を超えたクエリは PostgreSQL のログにも常時記録される。

注意が2点ある。
開発サーバーは同時ベットの実測で本番ビルドの約5倍遅く、性能判断に使えない。
判断は必ず本番ビルドで行う。
また perf:load の payout シナリオはレースを確定させるため、再計測は perf:setup からやり直す。

## シナリオと実測値

シナリオは8つある。

- login：全ユーザー同時ログイン。bcrypt の直列化の影響を単独実行と比較する
- bets：全ユーザー同時の単勝8点購入を3回繰り返す
- bulk：一人による三連単全4,896点の一括購入。1リクエストの書き込み最悪ケース
- peak：SSE 30接続、ページ閲覧、ベットが重なる開催ピークの複合負荷
- sse：締切イベントの全接続への到達遅延
- pages：主要5ページの応答
- payout：締切、着順確定、払戻確定の所要時間
- bot：無認証アクセス400件の混合実行

2026-09-04 時点の実測値を示す。
同時実行系の数値は95%のリクエストがその時間内に収まる応答時間、払戻確定は1回の所要時間である。
いずれもエラー0件、負荷後の台帳整合は全項目一致だった。

| 項目                 | 開発機 | 本番 VM | 判定基準  |
| -------------------- | ------ | ------- | --------- |
| 30人同時ベット       | 0.35秒 | 1.52秒  | 2秒未満   |
| 一斉ログイン         | 0.5秒  | 3.1秒   | 5秒未満   |
| SSE イベント到達     | 31ms   | 56ms    | 500ms未満 |
| ピーク時ページ応答   | 0.55秒 | 1.14秒  | 1秒未満   |
| 払戻確定 6,336ベット | 0.30秒 | 0.79秒  | 2秒未満   |

一斉ログインと30人同時ベットの開発機値は 2026-09-04 のチューニング後、本番 VM 値はチューニング前の実測であり、VM は次回デプロイ後に再計測する。

ピーク時ページ応答のみ基準を超えたが、これは30人が同時にベットを投げている数秒間に限った値である。
中央値は0.75秒でエラーはなく、バーストが終わればアイドル時の数十ミリ秒に戻るため、実用上の問題はないと判断した。

## 一人が行える購入の最悪ケース

1リクエストの購入点数上限 MAX_COMBINATIONS は 4,896 点である。
これは18頭フルゲートの三連単全点に相当し、UI のフォーメーションで組める理論最大と一致させてある。
上限に当たるのは不正リクエストだけであり、超過時は点数上限を明示するエラーを返す。

全点購入は bet と transaction 各4,896行の書き込みになるが、100行ずつのバッチ挿入により本番 VM でも1.1秒で完了する。
連投しても支出が残高とローンの上限で有界なため、書き込みを無限に増やす経路はない。
BET5 は何点分の購入でも1チケット1行で、書き込み増幅の構造を持たない。

## ロック設計と並行性

金融操作は advisory lock で保護されているが、placeBets のロックはウォレット単位である。
そのため30人が同時に購入しても互いに待ち合わず、同時実行時の応答時間の伸びはロック競合ではなく CPU の直列処理に由来する。
各負荷試験の後には reconcile で残高、取引台帳、ベットグループ、払戻状態の整合を検証しており、崩れは一度も出ていない。

## メモリ特性

本番プロセスは起動直後125MBで、負荷中も数百MBに収まる。
BOT トラフィックと認証済み負荷を混ぜた45分の連続ソークでは、約18万リクエストを流して RSS が248〜548MBの鋸歯状で推移し、単調増加は観測されなかった。
増えては GC が回収する正常なパターンであり、リークの兆候はない。

開発サーバーは長時間稼働で10GB超まで肥大することがあるが、これは next dev のホットリロードによる蓄積で、本番構成には存在しない。
開発機で気になったときはコンテナの再起動で回収できる。

保険として本番 compose には mem_limit を設定してある。
app 1GB、db 512MB、redis 256MB、tunnel 128MB で、実測ピークの約2倍の余裕がある。
万一の異常増加時は該当コンテナだけが OOM で再起動し、restart ポリシーにより自己回復する。

## 無認証アクセスと防御コスト

BOT の機械的アクセスは安価に処理される。
本番 VM の実測で、実在しないパスへの404と保護 API の401は十数ミリ秒で返り、レンダリングを伴う未認証トップでも95%が0.4秒以内に収まる。

ログイン失敗だけは bcrypt 照合を必ず通すため、本番 VM で1回あたり約150ミリ秒の CPU を消費する。
ただしレート制限が IP ごとに3〜5回で発動し、以降は照合前の軽い判定で弾かれる。
クライアント IP は Cloudflare が付け直す cf-connecting-ip だけを信頼する設計のため、ヘッダ偽装でレート制限は回避できない。
失敗記録は IP ごとに約100バイト、TTL 24時間の Redis キーであり、蓄積し続けることはない。

## 本番 VM の構成と知見

確定構成は vCPU 2、メモリ4GB固定、CPU タイプ host、SSD の discard 有効、自動起動と保護フラグ有効である。
実行時のメモリ使用は構成全体で0.5GB程度で、残りはデプロイ時に VM 上で走る next build のための余裕である。
ビルドの完走はメモリ8GB時に確認したもので、4GB 構成でのビルドは未検証である。不足したらビルドの間だけ割当を増やせばよい。

CPU タイプを汎用の x86-64-v2-AES から host に変えた前後で計測を比較したところ、改善は数パーセントの誤差程度だった。
この負荷の主要コストは JavaScript 実行であり、CPU タイプで露出が変わる命令セットの差が効く場面が少ないためと考えられる。
単一ノードではライブマイグレーションの互換性という host のデメリットが発生しないため、設定自体は維持している。

なお本番モードは Secure 接頭辞の Cookie 名を前提とするため、環境変数に https の AUTH_URL がないと管理画面が全て404になる。
負荷ツールはこの前提に合わせて全リクエストで x-forwarded-proto を https に偽装している。

## CPU 差の考察

開発機と VM ホストの仕様差を示す。

| 項目          | 開発機          | VM ホスト          |
| ------------- | --------------- | ------------------ |
| CPU           | Ryzen 9 9950X3D | Ryzen 7 PRO 4750GE |
| 世代          | Zen 5           | Zen 2              |
| 最大ブースト  | 約5.7GHz        | 約4.3GHz           |
| L3 キャッシュ | 128MB           | 8MB                |
| 電力枠        | 170W            | 35W                |

単一スレッド性能の実測差は、bcrypt によるログイン照合が物差しになる。
native 化前の同一の照合処理が開発機で56ミリ秒、VM で112ミリ秒と、2.0倍の差だった。
bcrypt は作業セットが小さくキャッシュにほぼ収まる計算主体の処理なので、この2.0倍はクロック比の約1.3倍に世代間の実行効率の差が乗ったものであり、キャッシュ容量に依存しない単一スレッド性能の下限差とみなせる。

一方、シナリオ全体の差は2〜3倍に分布し、計算主体の処理ほど2倍に近く、ページレンダリングや複合負荷ほど3倍側に寄った。
ページレンダリングはモジュール群やセッション処理を横断して作業セットが大きく、8MB の L3 では開発機の 128MB と違ってキャッシュから溢れやすい。
この差にメモリ世代の帯域差と仮想化のオーバーヘッドが上乗せされ、3倍側に寄ると考えられる。
ただしキャッシュ要因を単独で切り分けた実験はしておらず、実測で確定しているのは bcrypt の2.0倍だけである。

実務上の含意として、VM 側の将来の増強で効くのはコア数ではなくシングルコア性能であり、世代の新しい CPU への置き換えがそのまま応答時間の短縮になる。
host 化が誤差程度だった事実もこの見立てと整合する。性能を決めているのは素の実行性能とキャッシュであり、仮想 CPU の設定で埋まる差ではない。
